# Контракты агентов

Все агенты работают вокруг общего объекта `ProcessState`. Оркестратор передаёт агенту состояние процесса, агент возвращает структурированный `AgentResult`, после чего результат записывается обратно в Blackboard.

Текущая реализация не ограничивается заранее помеченными тест-кейсами. Агенты дополнительно используют `databases/oilcode_agent_test.db` как исторический контекст: DQ Agent сравнивает текущие значения с историческим распределением, Quality Agent обучает регрессионную модель серы по КИП 24-2000, Reliability Agent считает риск по статистическим компонентам, а Scenario Agent генерирует сценарии через перебор delta и чувствительности модели.

Базовый контракт:

```text
input: ProcessState
output: AgentResult
```

## Общий `ProcessState`

На входе у агентов должен быть единый временной срез:

- `timestamp` - время принятия решения;
- `avt_telemetry` - значения КИП АВТ;
- `unit_242000_telemetry` - значения КИП 24-2000;
- `latest_lims` - последние лабораторные значения до `timestamp`;
- `latest_pak` - последние значения ПАК до `timestamp`;
- `features` - лаги, rolling-признаки, возраст анализов, расхождения источников;
- `agent_results` - результаты уже выполненных агентов.

Приоритет источников качества:

```text
ЛИМС -> ПАК -> ВАК -> КИП
```

## `dq_agent.py`

### Что принимает

`ProcessState` с исходными телеметрическими и качественными данными:

- КИП АВТ;
- КИП 24-2000;
- последний ЛИМС;
- последний ПАК;
- возраст ЛИМС и ПАК;
- список критичных тегов;
- справочник тегов.

### Как анализирует

Проверяет:

- пропуски в критичных тегах;
- дубли времени;
- свежесть ЛИМС и ПАК;
- аномальные скачки;
- flatline-сигналы;
- расхождение ПАК со свежим ЛИМС;
- возможность продолжать расчёт;
- возможность выдавать операторскую рекомендацию.

Дополнительно рассчитывает исторические `p05`, `p50`, `p95`, `robust z-score` через MAD, flatline в последнем окне, тренд сигнала и конфликт ЛИМС/ПАК по сере.

### Что выдаёт

`AgentResult` вида:

```json
{
  "data_status": "limited",
  "confidence": 0.72,
  "freshness": {
    "lims_age_hours": 18.5,
    "pak_age_minutes": 10
  },
  "missing_critical_tags": ["F26"],
  "anomalies": ["flatline F9"],
  "statistical_checks": {
    "T5": {
      "value": 360.3,
      "median": 360.1,
      "p05": 354.2,
      "p95": 366.8,
      "robust_z": 0.2
    }
  },
  "source_priority_used": {
    "sulfur": "PAK",
    "D15": "LIMS"
  },
  "can_continue": true,
  "can_recommend": true,
  "blocking_reasons": []
}
```

## `quality_agent.py`

### Что принимает

`ProcessState` после DQ:

- статус качества данных;
- ЛИМС;
- ПАК;
- ВАК-формулы или рассчитанные ВАК-показатели;
- КИП-признаки АВТ и 24-2000;
- лаги и rolling-признаки;
- источник качества, которому доверяем по каждому показателю.

### Как анализирует

Оценивает текущее и прогнозное качество продукта:

- содержание серы;
- плотность `D15`;
- фракционный состав;
- температуру помутнения и другие показатели, если хватает данных;
- риск выхода за спецификацию;
- уверенность прогноза.

ЛИМС имеет приоритет над ПАК, ПАК - над ВАК, ВАК - над косвенными КИП-признаками.

В текущей реализации агент обучает линейную регрессию:

```text
target: 24-2000:Mg.Sulfur
features: T5, T6, P13, F9, F15, F26
```

Модель строится на пересечении `unit_242000_telemetry.date` и `pak_measurements.timestamp`. Затем агент считает прогноз модели, сравнивает модель с ЛИМС/ПАК, смешивает измерение и модель по весу доверия к источнику и добавляет uncertainty margin на основе RMSE и DQ.

### Что выдаёт

```json
{
  "model": {
    "status": "trained",
    "sample_count": 95,
    "r2": 0.7347,
    "rmse": 0.3406,
    "coefficients": {}
  },
  "current_quality": {
    "sulfur_mg_kg": 7.8,
    "d15_kg_m3": 831.2
  },
  "model_quality": {
    "sulfur_mg_kg": 7.9,
    "source_gap_mg_kg": 1.2,
    "blended_current_sulfur_mg_kg": 9.1,
    "uncertainty_margin_mg_kg": 0.34
  },
  "forecast_quality": {
    "sulfur_mg_kg": 8.6,
    "d15_kg_m3": 832.0
  },
  "spec_risks": {
    "sulfur_limit_10_mg_kg": "medium"
  },
  "confidence": 0.76,
  "main_drivers": ["ПАК свежий, ЛИМС устарел"],
  "hard_violations": []
}
```

## `reliability_agent.py`

### Что принимает

`ProcessState` после DQ:

- температуры;
- давления;
- перепады;
- расходы;
- изменения режима за последний час или смену;
- статус качества входных данных.

### Как анализирует

Оценивает тяжесть режима и прокси-риск для оборудования или катализатора:

- близость температуры к верхней модельной границе;
- рост перепада давления;
- резкие изменения расходов;
- нахождение около исторического экстремума;
- несогласованные изменения связанных сигналов.

В текущей реализации риск считается как сумма компонентов по `T5`, `P13`, `F26`, `F9`, `F15`. Для каждого компонента используются исторический профиль `p05/p50/p95`, `robust z-score`, тренд в последнем окне и направление риска для температур, давления и расходов.

### Что выдаёт

```json
{
  "risk_score": 0.64,
  "risk_class": "elevated",
  "risk_components": {
    "T5": {
      "value": 360.3,
      "component_score": 0.42,
      "weighted_score": 0.147
    }
  },
  "limiting_factors": [
    "температура реактора близка к верхней модельной границе"
  ],
  "forbidden_changes": [
    {
      "parameter": "T5",
      "direction": "increase",
      "reason": "дальнейшее повышение увеличивает тяжесть режима"
    }
  ],
  "confidence": 0.7
}
```

## `scenario_agent.py`

### Что принимает

Обновлённый `ProcessState`:

- результат DQ Agent;
- результат Quality Agent;
- результат Reliability Agent;
- список потенциально управляемых параметров;
- модельные диапазоны;
- ограничения качества;
- запреты на изменения.

### Как анализирует

Генерирует кандидатные варианты действий. Агент не выбирает финальную рекомендацию и не пишет операторское объяснение.

Текущая реализация перебирает несколько малых изменений для каждого доступного управляемого параметра:

- `T5`: несколько шагов вверх/вниз в градусах;
- `F26`, `F9`, `F30`: процентные изменения от текущего значения;
- все proposed-значения проверяются на модельные диапазоны.

Ожидаемая сера считается через чувствительность из Quality-модели. Ожидаемый риск корректируется через response-функцию и затем проверяется Safety Gate.

### Что выдаёт

```json
{
  "candidate_scenarios": [
    {
      "scenario_id": "S1",
      "changes": [
        {
          "parameter": "T5",
          "current": 365,
          "proposed": 362,
          "unit": "C"
        }
      ],
      "expected_effect": {
        "sulfur_mg_kg": 8.7,
        "reliability_risk_score": 0.58,
        "production_proxy": -0.01,
        "energy_proxy": -0.03
      },
      "confidence": 0.74
    }
  ]
}
```

## `safety_gate.py`

### Что принимает

Кандидатные сценарии и весь обновлённый `ProcessState`.

### Как анализирует

Отбрасывает сценарии, которые нельзя рекомендовать оператору:

- прогноз серы выше `10 mg/kg`;
- качество выходит за спецификацию;
- параметр не подтверждён как управляемый;
- сценарий выходит за модельный диапазон;
- Reliability Agent запретил такое изменение;
- данных недостаточно для безопасной рекомендации;
- доли блендинга не составляют 100%, если сценарий затрагивает блендинг.

### Что выдаёт

```json
{
  "accepted_scenarios": ["S1"],
  "rejected_scenarios": [
    {
      "scenario_id": "S2",
      "reason": "forecast_sulfur_mg_kg > 10"
    }
  ],
  "can_issue_recommendation": true
}
```

## `orchestrator.py`

### Что принимает

Исходный `ProcessState` или ссылку на запись из `process_state_snapshots`.

### Как анализирует

Оркестратор не является экспертной моделью. Он управляет порядком выполнения:

1. запускает DQ Agent;
2. останавливает расчёт, если `can_continue = false`;
3. запускает Quality Agent и Reliability Agent;
4. записывает результаты в Blackboard;
5. запускает Scenario Agent;
6. передаёт сценарии в Safety Gate;
7. запускает ranking;
8. формирует `RecommendationPacket`.

### Что выдаёт

```json
{
  "step": "safety_gate",
  "status": "completed",
  "next_step": "ranking",
  "reason": "accepted_scenarios is not empty"
}
```

## `blackboard.py`

### Что принимает

Исходный `ProcessState` и все `AgentResult`, которые возвращают агенты.

### Как анализирует

Blackboard не принимает решение самостоятельно. Он хранит общее состояние:

- исходный срез процесса;
- качество данных;
- прогноз качества;
- риск оборудования;
- кандидатные сценарии;
- причины отсева;
- выбранный сценарий.

### Что выдаёт

Обновлённый `ProcessState`, пригодный для следующего шага оркестратора.
