# Предварительная архитектура системы Нефтекод

Этот раздел описывает предварительную архитектуру мультиагентной системы для задачи Нефтекод. Архитектура читается слева направо: от источников данных к обработке, анализу состояния, генерации сценариев, фильтрации и выдаче рекомендации оператору.

Главная идея: система не должна сразу просить LLM выдать совет. Сначала данные проходят воспроизводимую обработку, затем специализированные аналитические модули считают качество данных, качество продукта и риск режима. После этого отдельный оптимизационный слой создаёт варианты управляющих воздействий, жёсткий фильтр отбрасывает недопустимые варианты, а LLM используется только для объяснения уже проверенного результата.

## Основной контур

```text
Источники данных
  -> Загрузка и очистка
  -> Синхронизация по времени и признаки
  -> ProcessState / Blackboard
  -> Оркестратор запускает аналитические модули
  -> DQ Checker
  -> Quality Agent
  -> Reliability Agent
  -> обновление ProcessState
  -> Scenario Optimizer
  -> Safety Gate
  -> Pareto / Ranking
  -> Recommendation Packet
  -> LLM Explainer
  -> готовая рекомендация оператору
```

## Роль оркестратора

Оркестратор управляет каждым шагом и решает, можно ли переходить на следующий слой архитектуры. Он не прогнозирует качество продукта, не считает риск оборудования и не генерирует текст рекомендации самостоятельно.

Оркестратор отвечает за:

- запуск этапов в правильном порядке;
- передачу общего `ProcessState` между слоями;
- проверку структурированного результата каждого модуля;
- остановку пайплайна при критически плохих данных;
- запрет недопустимых веток расчёта;
- сохранение логов и промежуточных результатов;
- подготовку финального `Recommendation Packet` для LLM.

Пример ветвления:

```text
DQ Checker вернул can_continue = false
  -> оркестратор не запускает Quality Agent, Reliability Agent и Scenario Optimizer
  -> формирует отказ: данных недостаточно

Reliability Agent вернул forbidden_changes = ["increase T5"]
  -> Scenario Optimizer не имеет права предлагать повышение T5

Safety Gate вернул accepted_scenarios = []
  -> оркестратор формирует отказ: безопасных сценариев нет
```

## Почему агенты не являются LLM

В этой архитектуре агент означает логическую роль с понятными входами, выходами и зоной ответственности. Агент не обязан быть нейросетью или LLM.

| Компонент | Чем является по сути |
|---|---|
| `DQ Checker` | набор правил и статистических проверок |
| `Quality Agent` | ВАК-формулы, ML или регрессионная модель качества |
| `Reliability Agent` | скоринговая функция и набор правил |
| `Scenario Optimizer` | алгоритм генерации и оценки сценариев |
| `Safety Gate` | строгие правила допустимости |
| `Pareto / Ranking` | Pareto-алгоритм или скоринговая функция |
| `LLM Explainer` | языковая модель для финального объяснения |

Такое разделение нужно, потому что численные прогнозы, ограничения и допустимость режима должны быть воспроизводимыми. LLM не должна решать, превышает ли сера 10 мг/кг, свежий ли ЛИМС или безопасно ли повышать температуру. Она может только объяснить уже рассчитанное решение.
