# Пайплайн архитектуры слева направо

Документ описывает каждый слой текущей схемы. Для каждого шага указано: что приходит, что происходит, какие инструменты используются и что выходит.

## 1. Источники данных

### Что приходит

На вход системы поступают все доступные источники по цепочке АВТ -> 24-2000 -> блендинг:

- `data/avt_tags.csv` - 10-минутная телеметрия АВТ: температуры, давления, расходы, уровни и другие КИП-сигналы.
- `data/242000_tags.csv` - 10-минутная телеметрия установки 24-2000: гидроочистка и стабилизация.
- `ЛИМСы ...xlsx` - лабораторные анализы качества по точкам отбора. Это контрольный источник качества.
- `Выгрузка ПАК ...xlsx` - поточные анализаторы: сера и плотность `D15`.
- `Теги_хакатон.xlsx` - справочник ЛА, ВАК, ПАК и КИП.
- `АВТ_схемы.pdf` - технологическая схема для понимания физического смысла узлов АВТ и выбора управляемых параметров.

### Что происходит

На этом этапе данные ещё считаются сырыми. Система только фиксирует, какие источники доступны и какую роль они играют в дальнейшем пайплайне.

Важно: `242000_tags.csv` не является ПАК. Это КИП-телеметрия установки 24-2000. ПАК - отдельный Excel с поточной серой и `D15`.

### Инструменты

- файловые загрузчики CSV/XLSX/PDF;
- конфигурация путей к источникам;
- схема описания источников;
- журнал загрузки.

### Что выходит

Список доступных источников и их ролей:

```json
{
  "sources": {
    "avt_telemetry": "data/avt_tags.csv",
    "unit_242000_telemetry": "data/242000_tags.csv",
    "lims": "ЛИМСы ...xlsx",
    "pak": "Выгрузка ПАК ...xlsx",
    "tag_catalog": "Теги_хакатон.xlsx",
    "process_scheme": "АВТ_схемы.pdf"
  }
}
```

## 2. Загрузка и очистка данных

### Что приходит

Сырые таблицы из CSV и Excel, а также справочник тегов.

### Что происходит

Система приводит источники к технически пригодному виду:

- удаляет служебные колонки `Unnamed`;
- приводит даты к единому формату;
- приводит числовые поля к числовым типам;
- нормализует единицы измерения;
- связывает короткие теги с расшифровкой из листа `КИП`;
- преобразует ЛИМС и ПАК из широкого формата в длинный формат;
- фиксирует подозрительные единицы измерения и явные допущения.

ЛИМС и ПАК нельзя соединять с телеметрией по номеру строки. Они имеют другую частоту и покрытие.

### Инструменты

- `pandas` или `polars`;
- Excel parser для `.xlsx`;
- словарь тегов из `Теги_хакатон.xlsx`;
- набор правил нормализации единиц;
- лог ошибок и пропусков.

### Что выходит

Очищенные таблицы:

```text
clean_avt_telemetry
clean_242000_telemetry
clean_lims_long
clean_pak_long
tag_catalog
vak_formulas
```

## 3. Синхронизация по времени, лаги и признаки

### Что приходит

Очищенные таблицы АВТ, 24-2000, ЛИМС, ПАК и справочников.

### Что происходит

Система строит временной срез процесса для выбранного момента `t`:

- объединяет телеметрию АВТ и 24-2000 по 10-минутному ключу `date`;
- для ЛИМС и ПАК берёт последнее измерение не позже `t`;
- считает возраст ЛИМС и ПАК;
- считает лаги технологических параметров;
- считает скользящие средние и изменения режима;
- считает расхождение между ПАК и последним ЛИМС;
- подготавливает входы для ВАК-формул;
- не использует будущие измерения качества для прошлого момента.

Влияние режима на качество может запаздывать, поэтому лаги должны быть явной частью признаков.

### Инструменты

- time-based join;
- `merge_asof` или аналог;
- rolling windows;
- lag features;
- календарная валидация без перемешивания строк;
- функции расчёта ВАК.

### Что выходит

Подготовленные признаки для выбранного момента:

```json
{
  "timestamp": "2026-08-07 00:00:00",
  "features": {
    "T5_lag_1h": 363.8,
    "T5_rolling_6h": 364.4,
    "F26_delta_1h": -120.5,
    "pak_lims_sulfur_delta": -0.3
  }
}
```

## 4. ProcessState / первая доска

### Что приходит

Синхронизированный временной срез и рассчитанные признаки.

### Что происходит

Формируется единый объект состояния процесса. Это первая доска, или исходный `ProcessState`. Здесь ещё нет выводов агентов и нет рекомендаций. Доска отвечает на вопрос: что мы знаем о процессе прямо сейчас?

### Инструменты

- `pydantic` или `dataclasses` для строгой структуры состояния;
- JSON-сериализация;
- схемы валидации;
- логирование снапшота.

### Что выходит

Единый исходный срез:

```json
{

  "avt_telemetry": {
```

## 5. Оркестратор

### Что приходит

Исходный `ProcessState`.

### Что происходит

Оркестратор запускает следующие модули, проверяет их результат и решает, можно ли идти дальше. Он работает как управляющий цикл:

1. запускает `DQ Checker`;
2. если данные критически плохие, останавливает пайплайн;
3. запускает `Quality Agent` и `Reliability Agent`;
4. записывает результаты в `ProcessState`;
5. запускает `Scenario Optimizer`;
6. запускает `Safety Gate`;
7. запускает Pareto-ranking;
8. готовит пакет для LLM.

### Инструменты

- pipeline controller;
- finite-state machine или обычный Python workflow;
- схемы входов и выходов агентов;
- обработчик ошибок;
- audit log.

### Что выходит

Обновляемый `ProcessState` и решение о переходе на следующий слой:

```json
{
  "step": "dq_checker",
  "status": "completed",
  "next_step": "quality_and_reliability",
  "reason": "DQ Checker returned can_continue = true"
}
```

## 6. Аналитические модули

### Что приходит

Каждый модуль получает `ProcessState`, но использует только свою часть данных.

### Что происходит

Аналитические модули не генерируют финальную рекомендацию. Они возвращают структурированный анализ:

- `DQ Checker` оценивает пригодность данных;
- `Quality Agent` оценивает текущее и прогнозное качество;
- `Reliability Agent` оценивает тяжесть режима и запрещённые изменения.

### Инструменты

- правила и статистические проверки;
- ВАК-формулы;
- ML/регрессионные модели;
- скоринговые функции;
- модельные диапазоны;
- структурированный JSON output.

### Что выходит

Выводы агентов записываются обратно в тот же `ProcessState`.

```json
{
  "data_quality": {
    "data_status": "limited",
    "confidence": 0.72,
    "can_continue": true
  },
  "quality_state": {
    "forecast_sulfur_mg_kg": 8.6,
    "sulfur_risk": "medium",
    "confidence": 0.76
  },
  "reliability_state": {
    "risk_score": 0.64,
    "risk_class": "elevated",
    "forbidden_changes": ["increase T5"]
  }
}
```

## 7. Обновлённая доска состояния

### Что приходит

Исходный `ProcessState` плюс результаты аналитических модулей.

### Что происходит

Это не отдельная вторая база и не новый независимый слой. Это тот же `ProcessState`, только обогащённый выводами агентов.

Он теперь отвечает на вопросы:

- можно ли доверять данным;
- есть ли риск по качеству;
- насколько тяжёлый режим;
- какие изменения уже запрещены;
- можно ли переходить к генерации сценариев.

### Инструменты

- JSON schema;
- validation;
- audit snapshots;
- версионирование состояния.

### Что выходит

Подготовленная основа для `Scenario Optimizer`.

## 8. Scenario Optimizer

### Что приходит

Обновлённый `ProcessState`, в котором уже есть:

- текущий режим;
- качество данных;
- прогноз качества;
- риск оборудования;
- запрещённые изменения;
- список управляемых параметров;
- модельные диапазоны.

### Что происходит

`Scenario Optimizer` создаёт кандидатные варианты управляющих воздействий. Он не принимает финальное решение. Его задача - предложить несколько возможных сценариев, которые затем будут проверяться.

Примеры сценариев:

- снизить температуру `T5` на 3 C;
- снизить расход `F26` на 2%;
- оставить режим без изменений;
- изменить соотношение потоков в пределах разрешённого диапазона.

### Инструменты

- grid search;
- эвристические правила;
- локальная оптимизация;
- модельный прогноз эффекта;
- ограничения на управляемые параметры;
- генератор сценариев.

### Что выходит

Список кандидатных сценариев:

```json
{
  "candidate_scenarios": [
    {
      "scenario_id": "S1",
      "changes": [
        {
          "parameter": "T5",
          "current": 365,
          "proposed": 362,
          "unit": "C"
        }
      ],
      "expected_effect": {
        "sulfur_mg_kg": 8.7,
        "reliability_risk_score": 0.58,
        "production_proxy": -0.01,
        "energy_proxy": -0.03
      },
      "confidence": 0.74
    }
  ]
}
```

## 9. Safety Gate

### Что приходит

Кандидатные сценарии и весь контекст из `ProcessState`.

### Что происходит

Safety Gate проверяет не сами JSON-выводы агентов, а именно сценарии управляющих воздействий. Он отбрасывает варианты, которые нельзя рекомендовать оператору.

Сценарий считается недопустимым, если:

- прогноз серы выше 10 мг/кг;
- качество выходит за выбранную спецификацию;
- параметр не подтверждён как управляемый;
- сценарий выходит за модельный или технологический диапазон;
- Reliability Agent запретил соответствующее изменение;
- данных недостаточно для безопасной рекомендации;
- доли блендинга не составляют 100%, если блендинг участвует в сценарии.

### Инструменты

- rule engine;
- проверка схемы сценариев;
- список hard constraints;
- список rejected reasons;
- журнал отсевов.

### Что выходит

Список принятых и отклонённых сценариев:

```json
{
  "accepted_scenarios": ["S1", "S4"],
  "rejected_scenarios": [
    {
      "scenario_id": "S2",
      "reason": "forecast_sulfur_mg_kg > 10"
    },
    {
      "scenario_id": "S3",
      "reason": "parameter T5 increase is forbidden by Reliability Agent"
    }
  ],
  "can_issue_recommendation": true
}
```

## 10. Pareto / Ranking

### Что приходит

Только сценарии, прошедшие Safety Gate.

### Что происходит

Система сравнивает допустимые сценарии по нескольким критериям. Важно: Pareto или скоринг применяются только после жёсткой фильтрации. Недопустимый сценарий не может быть выбран из-за хорошего выпуска или низких энергозатрат.

Критерии:

1. качество продукта;
2. риск оборудования;
3. выпуск или production proxy;
4. энергозатраты или cost proxy;
5. уверенность прогноза.

### Инструменты

- Pareto front;
- weighted scoring;
- lexicographic ranking;
- tie-break rules;
- таблица сравнения сценариев.

### Что выходит

Лучшие допустимые сценарии и причина выбора:

```json
{
  "ranked_scenarios": [
    {
      "scenario_id": "S1",
      "rank": 1,
      "why": "best balance between sulfur risk and reliability risk"
    },
    {
      "scenario_id": "S4",
      "rank": 2,
      "why": "higher production but lower confidence"
    }
  ]
}
```

## 11. Recommendation Packet

### Что приходит

Результат ranking, причины отсева Safety Gate, ключевые выводы агентов и общий статус данных.

### Что происходит

Формируется компактный пакет для финального объяснения. В LLM не передаются все сырые данные, все строки телеметрии и все промежуточные признаки. LLM получает только сжатый проверенный контекст.

### Инструменты

- шаблон `RecommendationPacket`;
- JSON schema;
- ограничение размера контекста;
- список обязательных полей для объяснения.

### Что выходит

Компактный пакет:

```json
{
  "decision": "recommend",
  "selected_scenario": "S1",
  "problem": "medium sulfur risk with elevated reliability risk",
  "action": "decrease T5 by 3 C",
  "expected_quality": {
    "sulfur_mg_kg": 8.7,
    "limit": 10
  },
  "reliability": {
    "risk_score": 0.58,
    "risk_class": "acceptable"
  },
  "confidence": "medium",
  "confidence_reason": "LIMS is stale, PAK is fresh",
  "rejected_scenarios": [
    {
      "scenario_id": "S2",
      "reason": "forecast_sulfur_mg_kg > 10"
    }
  ]
}
```

## 12. LLM Explainer

### Что приходит

Только `Recommendation Packet`.

### Что происходит

LLM не считает серу, не проверяет ограничения и не выбирает сценарий из сырых данных. Она превращает готовое решение в понятное оператору объяснение.

### Инструменты

- LLM;
- шаблон операторского сообщения;
- проверка на отсутствие неподтверждённых фактов;
- ограничение формата ответа.

### Что выходит

Финальный текст:

```text
Рекомендуется сценарий S1: снизить T5 на 3 C.
Этот вариант выбран, потому что прогноз по сере остаётся ниже 10 мг/кг,
а риск тяжёлого режима снижается. Уверенность средняя: последний ЛИМС
устарел, поэтому расчёт опирается на свежий ПАК и ВАК.
```

## 13. Выдача готовых рекомендаций

### Что приходит

Текст LLM и структурированный `Recommendation Packet`.

### Что происходит

Система показывает оператору рекомендацию и сохраняет все технические основания решения.

### Инструменты

- dashboard;
- CLI или API;
- audit log;
- сохранение входного `ProcessState`, agent results, Safety Gate и ranking.

### Что выходит

Оператор видит:

- проблему или риск;
- предлагаемое действие;
- ожидаемый эффект;
- проверенные ограничения;
- уверенность;
- причины отсева альтернатив;
- сообщение об отказе, если безопасной рекомендации нет.
