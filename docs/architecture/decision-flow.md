# Генерация сценариев, фильтрация и финальная рекомендация

Этот документ описывает финальную часть архитектуры: как из анализа состояния процесса получается рекомендация оператору.

## Что такое сценарий

Сценарий - это не JSON-вывод DQ Checker, Quality Agent или Reliability Agent. Сценарий появляется только после работы `Scenario Optimizer`.

Сценарий означает кандидатный вариант управляющего воздействия:

```json
{
  "scenario_id": "S1",
  "changes": [
    {
      "parameter": "T5",
      "current": 365,
      "proposed": 362,
      "unit": "C"
    }
  ],
  "expected_effect": {
    "sulfur_mg_kg": 8.7,
    "reliability_risk_score": 0.58,
    "production_proxy": -0.01,
    "energy_proxy": -0.03
  },
  "confidence": 0.74
}
```

Выводы первых агентов описывают текущее состояние. Сценарии описывают возможные будущие действия.

## Где появляются сценарии

Сценарии создаёт `Scenario Optimizer`.

Он получает:

- текущий режим из `ProcessState`;
- статус данных от `DQ Checker`;
- прогноз качества от `Quality Agent`;
- риск режима от `Reliability Agent`;
- запрещённые изменения;
- список управляемых параметров;
- модельные диапазоны;
- ограничения качества.

Он выдаёт:

- набор кандидатных сценариев;
- ожидаемый эффект по каждому сценарию;
- confidence по каждому сценарию;
- технические причины, почему сценарий был сформирован.

## Что такое опасный или недопустимый сценарий

Опасный сценарий - это не плохой JSON агента. Это вариант управляющего воздействия, который нельзя рекомендовать оператору.

Сценарий недопустим, если:

- прогноз серы выше `10 mg/kg`;
- качество выходит за спецификацию;
- параметр не подтверждён как управляемый;
- изменение запрещено Reliability Agent;
- сценарий выходит за модельный диапазон;
- данные слишком плохие для рекомендации;
- сценарий ухудшает уже критичное состояние;
- блендинг не сохраняет сумму долей 100%.

## Safety Gate

Safety Gate - это обязательный слой перед любым ранжированием. Он работает по строгим правилам.

### Что приходит

```text
candidate_scenarios
+ data_quality
+ quality_state
+ reliability_state
+ controlled_parameters
+ model_ranges
+ hard_constraints
```

### Что происходит

Safety Gate проверяет каждый сценарий:

1. Все изменяемые параметры входят в whitelist управляемых параметров.
2. Предложенные значения лежат в допустимых модельных или технологических диапазонах.
3. Прогноз серы не превышает `10 mg/kg`.
4. Риск оборудования не выше допустимого порога.
5. Не нарушены запреты Reliability Agent.
6. Уровень доверия к данным достаточен для рекомендации.
7. Для блендинга сумма долей компонентов равна 100%.

### Какие инструменты нужны

- rule engine;
- JSON schema validation;
- whitelist управляемых параметров;
- hard constraints;
- список причин отсева;
- audit log.

### Что выходит

```json
{
  "accepted_scenarios": ["S1", "S4"],
  "rejected_scenarios": [
    {
      "scenario_id": "S2",
      "reason": "forecast_sulfur_mg_kg > 10"
    },
    {
      "scenario_id": "S3",
      "reason": "parameter T5 increase is forbidden"
    }
  ],
  "can_issue_recommendation": true
}
```

Если `accepted_scenarios` пустой, оркестратор не должен пытаться просить LLM выбрать лучший вариант. Он должен сформировать отказ:

```text
Надёжной рекомендации нет: безопасных сценариев не найдено.
```

## Pareto / Ranking

Pareto и ranking работают только после Safety Gate.

### Что приходит

Только допустимые сценарии:

```text
accepted_scenarios
```

### Что происходит

Сценарии сравниваются по нескольким критериям:

- риск выхода за спецификацию качества;
- риск оборудования;
- выпуск или production proxy;
- энергия или cost proxy;
- уверенность прогноза.

Жёсткий приоритет:

```text
качество и безопасность
  > риск оборудования
  > выпуск
  > энергия / стоимость
  > уверенность прогноза
```

Недопустимый сценарий не может попасть в Pareto-front.

### Инструменты

- Pareto-front;
- lexicographic ranking;
- weighted scoring;
- таблица сравнения сценариев;
- правила tie-break.

### Что выходит

```json
{
  "ranked_scenarios": [
    {
      "scenario_id": "S1",
      "rank": 1,
      "quality_margin": "safe",
      "reliability_risk": "acceptable",
      "production_proxy": -0.01,
      "energy_proxy": -0.03,
      "confidence": 0.74
    },
    {
      "scenario_id": "S4",
      "rank": 2,
      "quality_margin": "safe",
      "reliability_risk": "acceptable",
      "production_proxy": 0.02,
      "energy_proxy": 0.01,
      "confidence": 0.62
    }
  ],
  "selection_reason": "S1 has lower sulfur risk and higher confidence"
}
```

## Recommendation Packet

Перед LLM нужно отправлять не весь `ProcessState`, а короткий пакет.

### Почему нельзя передавать всё

Полный Blackboard содержит слишком много данных:

- исходную телеметрию;
- лаги и rolling-признаки;
- промежуточные вычисления;
- все кандидатные сценарии;
- технические логи;
- сырые JSON всех модулей.

LLM не должна всё это анализировать. Она должна получить уже проверенное решение.

### Что входит в пакет

```json
{
  "decision": "recommend",
  "selected_scenario": "S1",
  "action": "decrease T5 by 3 C",
  "expected_quality": {
    "sulfur_mg_kg": 8.7,
    "limit": 10
  },
  "reliability": {
    "risk_score": 0.58,
    "risk_class": "acceptable"
  },
  "confidence": "medium",
  "confidence_reason": "LIMS is stale, PAK is fresh",
  "rejected_scenarios": [
    {
      "scenario_id": "S2",
      "reason": "forecast_sulfur_mg_kg > 10"
    }
  ],
  "alternatives": [
    {
      "scenario_id": "S4",
      "tradeoff": "higher production but lower confidence"
    }
  ]
}
```

## Роль LLM

LLM используется как `Explainer`, а не как расчётный агент.

### Что LLM делает

- формулирует понятную рекомендацию;
- объясняет, почему выбран сценарий;
- объясняет, почему альтернативы отброшены;
- показывает уровень уверенности;
- пишет операторский текст в едином стиле.

### Что LLM не делает

- не прогнозирует серу;
- не считает `D15`;
- не проверяет диапазоны;
- не решает, свежий ли ЛИМС;
- не выбирает недопустимый сценарий;
- не заменяет Safety Gate;
- не придумывает физический смысл тега без справочника.

## Финальный ответ

Итоговый ответ оператору должен иметь структуру:

```text
1. Время и состояние
2. Обнаруженная проблема или риск
3. Предлагаемое действие
4. Ожидаемый эффект
5. Проверенные ограничения
6. Уверенность
7. Причины выбора и отсева альтернатив
```

Если безопасной рекомендации нет, система должна уметь отказаться:

```text
Надёжной рекомендации нет: последнее лабораторное значение устарело,
а доступные варианты либо нарушают ограничение по сере,
либо выходят за модельный диапазон.
```
