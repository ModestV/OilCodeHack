# Рекомендации и песочница: инструкция по интеграции

## Назначение ветки

Ветка добавляет интерактивные UI-разделы поверх существующего мониторинга. Для серверной интеграции доступен локальный детерминированный контур `QualityAgent → ReliabilityAgent → OptimizationAgent → Orchestrator`, который запускается через `POST /api/datasets/{id}/decision`. Внешний LLM не вызывается в smoke-контуре: логические роли отделены от расчётных инструментов и могут быть обёрнуты локальным LLM-адаптером в закрытой сети. Endpoint `POST /api/datasets/{id}/scenario` остаётся источником расчёта для редактируемой песочницы.

## Точки интеграции

- `frontend/src/App.tsx` владеет навигацией, выбранным датасетом и моментом `to`.
- `frontend/src/views/DecisionSupportView.tsx` остаётся единым внешним контейнером для двух режимов.
- `frontend/src/demo/decisionSupportDemo.ts` содержит только временные presentation fixtures.
- `frontend/src/api.ts` и `frontend/src/types.ts` содержат контракты `ScenarioRequest`/`ScenarioResult`/`DecisionResult`, включая модельный прогноз серы.
- `backend/app.py` предоставляет endpoint decision; `backend/agents.py` содержит роли, trace и правило abstain при недостатке базовых данных.

## Поток данных

Мониторинг выбирает датасет и момент. `App` передаёт в `DecisionSupportView` также название набора `datasetName` и `latestAt` (конец телеметрии, затем конец набора, затем выбранный момент). Рекомендации показывают последний доступный момент либо выбранный пользователем период. Даты контролируются состоянием; пустой или обратный период блокирует действие. Результат получает реальные данные через decision API; сценарные коэффициенты и прогноз Ridge явно помечены как модельные допущения.

Действие «Проверить в песочнице» выполняет переход через `onOpenSandbox(): void`; параметры сценария и период не передаются, поэтому песочница запускается с прозрачными начальными значениями. Выбор меняет поля; сброс возвращает выбранный набор. Расчёт использует `ScenarioRequest` и `/scenario`. При изменении входа прежний результат скрывается.

Если позже появится отдельный внешний recommendation service, он должен заменить только adapter и не менять navigation contract:

```ts
interface RecommendationContext {
  datasetId: string;
  from?: string;
  to: string;
  mode: "latest" | "period";
  source: "recommendation" | "monitoring" | "manual";
  recommendationId?: string;
  scenarioId?: string;
}
```

## UX-контракт

- Все три раздела находятся в одной навигации, активный обозначен одинаково и через `aria-current`.
- В рекомендациях сначала виден выбор данных и основное действие; после запуска — результат, затем таблица сравнения. На мобильном кнопка находится после дат.
- Этапы обработки находятся в закрытом блоке «Как получена рекомендация». Не возвращать на первый экран pipeline, adapter, заявления «Подтверждено» и декоративную уверенность.
- Таблица сравнения заменяет неработающую кнопку сравнения. «Скопировать текст» использует Clipboard API и сообщает об ошибке, если копирование недоступно.
- Песочница: исходные данные → условия расчёта → изменения режима → состав смеси → свёрнутые параметры модели → результат. Поля имеют постоянные подписи; коэффициенты не мешают основному пути.
- Не добавлять текст, который пересказывает соседние поля: «Начните с…», «Выберите … или переключитесь…», «Рекомендуемый путь». Помощь нужна для единиц, ошибок, неоднозначностей и ограничений расчёта.
- Сохранять короткую пометку об условных числах, источники измерений и ограничения модели. Не выдавать заглушку за реальный прогноз.
- В таблицах на телефоне прокручивается только таблица. Не заменять подписи полей placeholder-текстом.

Выбор UX-решений опирается на [NN/g: раскрытие сложных функций по запросу](https://www.nngroup.com/articles/progressive-disclosure/), [GOV.UK: подписи и краткие подсказки полей](https://design-system.service.gov.uk/components/text-input/) и [Carbon: сравнение данных в таблице](https://v10.carbondesignsystem.com/components/data-table/usage/). Это ориентиры для конкретных решений, не заявление о проведённом исследовании с операторами.

## Правила merge

1. Сохранить общую оболочку `App.tsx` и state мониторинга.
2. Не переименовывать и не ломать `ScenarioRequest`/`ScenarioResult`.
3. Подключать реальные pipeline endpoints через отдельный adapter вместо замены demo fixtures внутри представления.
4. При конфликте в `App.tsx` сохранить callback перехода в sandbox и существующий `datasetId`/`to`.
5. После подключения backend удалить demo-источник только после покрытия состояний loading, error, empty и partial data.

## Проверка после объединения

Запустить `npm run typecheck`, `npm run build` и frontend-тесты. Вручную проверить latest/period, переход рекомендация→песочница, выбор учебного набора, ручной режим, сброс, пересчёт, пустой датасет, предупреждения и mobile layout.

## Контур decision API

Тело `POST /api/datasets/{id}/decision` имеет тот же контракт `ScenarioRequest`, что и `/scenario`, поэтому клиент может передать только `at` и использовать значения по умолчанию. Ответ содержит `status: "recommendation" | "abstain"`, структурированные результаты `agents.quality`, `agents.reliability`, `agents.optimization`, краткий исполняемый `trace`, а также `recommendation` и `scenario` при успешном расчёте. Если baseline серы недоступен или не проходит проверку надёжности, `recommendation` и `scenario` равны `null`, а `abstain.reason` объясняет причину.

Отдельный `GET /api/datasets/{id}/forecast?at=ISO` запускает первую leakage-safe
модель серы. Сервис загружает `reports/modeling/sulfur-first-iteration/model.json`
и собирает признаки из LONG Parquet только до `at - 4 часа`: текущие значения,
прошлые скользящие средние и доступный на этом cutoff предыдущий ЛИМС результат.
Ответ содержит Ridge prediction, консервативный `prediction_risk_guard`, время
среза признаков и `leakage_check`. В `decision` этот же ответ доступен в
`forecast` и в `agents.quality.evidence.model_forecast`; отсутствие артефакта
остаётся объяснимым warning и не скрывает прозрачный сценарный fallback.

## Ограничения

Линейная модель сценариев прозрачна и редактируема, но не является промышленным оптимизатором. Decision-контур не подтверждает причинность коэффициентов и не заменяет инструкцию оператору; каждое решение должно проходить проверку свежести и качества данных.
